0.2 Table Creation (Raw Layer)

Customers:-

CREATE TABLE raw_customers (
    customer_id VARCHAR(50) PRIMARY KEY,
    customer_zip_code VARCHAR(20),
    customer_city VARCHAR(100),
    customer_state VARCHAR(50)
);

Script:-

“Then, I created the raw_customers table. It was designed to store each customer’s ID, zip code, city, and state. The customer_id served as the primary key, ensuring uniqueness and enabling clean joins with other tables. This structure laid the foundation for customer-level analytics.”

Orders:-

CREATE TABLE raw_orders (
    order_id VARCHAR(50) PRIMARY KEY,
    customer_id VARCHAR(50),
    order_status VARCHAR(30),
    order_purchase_timestamp DATETIME,
    order_approved_at DATETIME,
    order_delivered_timestamp DATETIME,
    order_estimated_delivery_date DATE
);

Script:-

“In this query, I had created the raw_orders table. It was designed to store each order’s ID, customer reference, status, key timestamps and dates such as purchase, approval, delivery, and estimated delivery date. The order_id served two purposes here, one as the primary key, it ensured each order was uniquely tracked and secondly, it helped in enabling accurate joins with other tables for lifecycle analysis.”

Order Items :-

CREATE TABLE raw_order_items (
    order_id VARCHAR(50),
    product_id VARCHAR(50),
    seller_id VARCHAR(50),
    price DECIMAL(10,2),
    shipping_charges DECIMAL(10,2)
);

Script:-

This table was designed to store the details of each item within an order, including the order ID, product ID, seller ID, item price, and shipping charges. This table acted as the line‑item level detail for orders, allowing us to break down each transaction into its individual components for more granular analysis.”

Payments:-

CREATE TABLE raw_payments (
    order_id VARCHAR(50),
    payment_sequential INT,
    payment_type VARCHAR(30),
    payment_installments INT,
    payment_value DECIMAL(10,2)
);

Script:-

This was designed to store payment details for each order, including the payment sequence, type, installments, and value. I had not defined a primary key here because one order could have multiple payment records, and forcing uniqueness would not reflect the raw transactional nature of the data. Instead, the design allowed flexibility to capture all payment events accurately.”

Products:-

CREATE TABLE raw_products (
    product_id VARCHAR(50) PRIMARY KEY,
    product_category_name VARCHAR(100),
    product_weight_g INT,
    product_length_cm INT,
    product_height_cm INT,
    product_width_cm INT
);

Script:-

“In this query, I had created the raw_products table. It was designed to store product details such as ID, category, weight, and dimensions including length, height, and width. The product_id was defined as the primary key, ensuring each product was uniquely identified. This structure allowed us to analyze product categories and physical attributes efficiently in large‑scale datasets.”

- negative price
- shipping cost higher than product price

Possible outcomes:
Case A — Data already clean
→ we directly move to analysis

Case B — Minor inconsistencies
→ we create clean analytical views

We never edit raw tables.

Query------------------------------------------------------------------------
SELECT
    order_month,
    monthly_revenue,
    SUM(monthly_revenue) OVER (ORDER BY order_month)
        AS cumulative_revenue
FROM
(
    SELECT
        DATE_FORMAT(o.order_purchase_timestamp, '%Y-%m') AS order_month,
        ROUND(SUM(oi.price),2) AS monthly_revenue
    FROM raw_orders o
    JOIN raw_order_items oi
        ON o.order_id = oi.order_id
    WHERE o.order_status = 'delivered'
    GROUP BY order_month

ORDER BY order_month;
